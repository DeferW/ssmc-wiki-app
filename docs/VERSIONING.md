# Версии сайта

Версия описывает то, что видит пользователь сайта, а не внутреннее устройство
кода. Формат — `MAJOR.MINOR.PATCH`, например `3.1.0`. Четвёртого числа нет:
сайт публикуется после каждого merge в `main`, а конкретную сборку определяет
короткий commit, который страница «Проект» показывает рядом с версией.

## Что увеличивать

| Число | Когда | Примеры |
|---|---|---|
| **MAJOR** | Новый модуль на главной (`planned` → `active`); переработка модуля, после которой им пользуются иначе или старые ссылки перестают работать; общий редизайн сайта | симулятор взрывов, «Комплект бойца» |
| **MINOR** | Новая функция внутри существующего модуля; новые игровые данные, которые стали видны на сайте; заметное ускорение или улучшение интерфейса | уровни крыши на картах, режим сравнения в калькуляторе, вкладка «Отдача» |
| **PATCH** | Исправления ошибок, правки текстов и стилей, пересборка данных под новый commit игры без новых полей, обновление зависимостей, тесты и рефакторинг | исправление falloff, исправление брони Бастиона |

При сомнении выбирается младшее число. При увеличении старшего числа младшие
сбрасываются: `3.4.2` → `3.5.0` → `4.0.0`.

## Как отмечать изменения

Номер не выбирается вручную. Автор PR только указывает тип своего изменения
отдельным файлом в [`.changes/`](../.changes/README.md):

```markdown
---
bump: minor
---
Карты: заливка зон по уровням крыши (1–4) с отдельными переключателями.
```

Один файл — одна строка журнала; в одном PR может быть несколько файлов.
Рефакторинг, тесты, документация и CI отметок не требуют. Отметки сразу видны
на странице «Проект» в разделе «Не выпущено» вместе с номером, который получит
следующая версия.

PR-проверка (`npm run changes:check`, в CI с `--base`):

- **ошибка**, если отметка не разбирается: нет блока `---`, неизвестный `bump`,
  лишнее поле или пустой текст;
- **ошибка**, если модуль в `src/modules/registry.tsx` стал `active`, а новой
  отметки `bump: major` нет;
- **предупреждение**, если изменён код сайта в `src/` (кроме тестов), а новых
  отметок нет. Оно не блокирует PR: внутренние изменения версию не двигают.

## Как выпускать

Версия выпускается вручную, когда изменения накопились.

1. На отдельной ветке `npm run release -- --dry-run` показывает будущий номер и
   список изменений, ничего не меняя.
2. `npm run release`:
   - берёт самый крупный `bump` среди отметок (`major` > `minor` > `patch`);
   - увеличивает номер и сбрасывает младшие числа;
   - добавляет в [`CHANGELOG.md`](../CHANGELOG.md) раздел с номером и датой;
   - обновляет `package.json` и `package-lock.json`;
   - удаляет использованные отметки.
3. Релизный PR с этими изменениями. После merge на его commit ставится тег:
   `git tag v3.2.0 && git push origin v3.2.0`.

`package.json` — единственный источник номера. Страница «Проект» получает его
при сборке (`__APP_VERSION__` в `vite.config.ts`). Тест проверяет, что последняя
версия в `CHANGELOG.md` совпадает с `package.json`. `CHANGELOG.md` вручную не
редактируется.

## Репозиторий данных

У `ssmc-wiki-data` нет собственной версии сайта. Совместимость данных
описывают `schemaVersion` каждого публичного контракта и `gameCommit` сборки.
