# Руководство контрибьютора SSMC Wiki

Это руководство описывает правила совместной разработки двух репозиториев:

- [`ssmc-wiki-data`](https://github.com/DeferW/ssmc-wiki-data) — воспроизводимые
  сборщики и публичные данные;
- [`ssmc-wiki-app`](https://github.com/DeferW/ssmc-wiki-app) — модульное
  веб-приложение, которое использует эти данные.

Документ намеренно не перечисляет существующие модули и их возможности. Он
фиксирует устойчивую архитектуру, по которой можно добавлять новые части проекта
без переписывания руководства.

## 1. Главная модель проекта

```text
исходники игры + редактируемая конфигурация
                    │
                    ▼
ssmc-wiki-data / scripts/<module_package>
read → resolve → normalize → validate → publish
                    │
                    ▼
data/<module-id>/ публичный контракт и ассеты
                    │
                    ▼
ssmc-wiki-app deploy: полная замена public/data
                    │
                    ▼
ssmc-wiki-app / src/modules/<module-id>
load → check schema → calculate/format → render
                    │
                    ▼
пользователь
```

Граница ответственности проста:

- сборщик знает, **как механика описана в игре**, и переводит её в устойчивую
  предметную модель;
- приложение знает, **как эту модель использовать и показывать**, но не
  разбирает игровые YAML, C# или внутренние отчёты сборщика;
- публичный JSON является контрактом между репозиториями.

Если сайту не хватает данных, поле сначала появляется в публичном контракте
`ssmc-wiki-data`. Временное копирование значения в TypeScript или ручная правка
generated JSON не считается решением.

## 2. Архитектурные правила

Эти правила обязательны для нового кода:

1. Предметная функциональность живёт в отдельном модуле.
2. Модуль владеет своими типами, вычислениями, тестами и публичной схемой.
3. Registry и общая оболочка только подключают модуль, но не реализуют его
   бизнес-логику.
4. Generated data меняются запуском сборщика, а не вручную.
5. Приложение читает только публичные контракты, а не диагностические файлы.
6. Общая абстракция появляется после второго реального применения.
7. Ломающее изменение получает новую `schemaVersion`.
8. Новая версия данных публикуется раньше приложения, которое начинает её
   требовать.
9. Большие наборы данных и ассеты загружаются лениво, а не одним запросом.
10. Секреты, пароли и административные токены не попадают в клиентский bundle.
11. Production читает deploy-снимок из `public/data`, а не обращается к GitHub
    Raw при каждом открытии модуля.

## 3. Границы модулей

Один канонический `module-id` следует использовать по всей вертикали, если
сборщик и интерфейс относятся к одной предметной области:

```text
ssmc-wiki-data/scripts/<module_package>/
ssmc-wiki-data/data/<module-id>/
ssmc-wiki-app/src/modules/<module-id>/
```

Используйте устойчивый идентификатор в `kebab-case`. Если составное имя нужно
импортировать как Python-пакет, замените дефисы на подчёркивания только в
`scripts/<module_package>/`; публичный ID, data-папка и URL остаются прежними.
Не включайте в идентификатор номер версии, статус или имя автора.

Модуль может использовать общую инфраструктуру, но не должен случайно зависеть
от внутренней реализации другого модуля. Допустимы небольшие явно устойчивые
границы: общий тип контракта, загрузчик опубликованного набора или примитивный
компонент отображения. Страницы, локальное состояние и внутренние компоненты
одного модуля не становятся API для другого.

Если один и тот же код понадобился второй предметной области:

1. определите минимальную общую часть;
2. отделите её от предметных правил первого модуля;
3. перенесите в существующий общий слой или создайте небольшой общий слой;
4. оставьте предметные адаптеры внутри модулей;
5. добавьте тесты на общую часть и оба использования.

Не создавайте универсальный фреймворк заранее. Небольшое дублирование до
появления понятной общей модели дешевле ошибочной абстракции.

## 4. Репозиторий данных

### 4.1. Структура

```text
config/                    редактируемые входные настройки
scripts/common/            чтение общих форматов и разделяемые примитивы
scripts/<module_package>/  код одного сборщика и его тесты
data/<module-id>/          опубликованные JSON и ассеты
.github/workflows/         проверки и воспроизводимая публикация
requirements.txt           runtime-зависимости сборщиков
pyproject.toml             настройки Python-инструментов
```

Типичная внутренняя структура сборщика:

```text
scripts/<module_package>/
  build.py                 CLI и порядок этапов
  validate.py              проверка опубликованного результата
  core/domain/...          предметные преобразования
  test_*.py                модульные и регрессионные тесты
```

Названия внутренних файлов выбираются по ответственности. Не требуется
копировать структуру другого модуля, если его конвейер устроен иначе.

### 4.2. Этапы сборки

У сборщика должны быть различимы следующие этапы:

1. **Read** — чтение точных источников игры и конфигурации.
2. **Resolve** — наследование прототипов, локализация и технические ссылки.
3. **Normalize** — перевод игровых компонентов в небольшую предметную модель.
4. **Relate** — связи между сущностями, если они нужны потребителю.
5. **Serialize** — детерминированная запись публичного JSON и ассетов.
6. **Validate** — проверка схемы, ссылок, диапазонов и файлов.

Не обязательно создавать по файлу на каждый этап, но границы должны быть видны
в коде и тестироваться отдельно от CLI.

### 4.3. Источники истины

Порядок приоритета:

1. игровые прототипы, локализация и код механики;
2. явная конфигурация репозитория;
3. нормализующая логика сборщика;
4. generated data.

Если значение является C#-значением по умолчанию и отсутствует в YAML,
допустимо хранить именованную константу в сборщике. Рядом укажите исходный
компонент или систему, добавьте тест и не маскируйте константу под значение,
автоматически полученное из игры. Такие зеркала нужно проверять при обновлении
игровой механики.

Конфигурация нужна для осознанного выбора источников и редакторских решений.
Она не должна становиться ручной копией игровых характеристик.

### 4.4. Нормализация

Публичный контракт описывает механику, а не конкретную верстку. Хорошее поле:

- имеет стабильный предметный смысл;
- не требует от сайта знать имя игрового компонента;
- использует числа, списки и структурированные объекты вместо готовой HTML-строки;
- присутствует только там, где семантически применимо;
- имеет однозначные единицы измерения;
- проверяется валидатором.

Не публикуйте весь игровой компонент «на будущее». Добавляйте большинство
полезных игроку данных, сохраняя возможность расширить блок необязательными
полями.

### 4.5. Публичные и внутренние документы

У каждого набора должна быть одна понятная публичная точка входа — обычно
`data/<module-id>/catalog.json` или небольшой manifest. Приложение начинает
загрузку с неё.

Диагностические индексы могут содержать сырой граф, происхождение значений и
промежуточные результаты. Они предназначены для разработчиков и валидатора:

- сайт на них не опирается;
- обратная совместимость для них не гарантируется;
- они не используются как обход отсутствующего поля в публичной схеме.

### 4.6. Версии схемы

Каждая публичная точка входа содержит `schemaVersion`.

Добавочное изменение обычно совместимо:

- новое необязательное поле;
- новый элемент перечисления, если потребитель умеет безопасно его пропустить;
- новый отдельный ассет, не меняющий существующие пути.

Ломающее изменение требует новой версии:

- удаление или переименование поля;
- изменение типа, единиц или смысла;
- изменение обязательности;
- смена структуры путей или идентификаторов;
- несовместимая семантика уже существующего значения.

Приложение должно явно проверять поддерживаемые версии и выдавать понятную
ошибку вместо молчаливого отображения неверных данных.

### 4.7. Детерминированность

Одинаковые исходники, конфигурация и commit игры должны давать одинаковый
результат. Поэтому:

- сортируйте словари и списки, если порядок не несёт игровой смысл;
- не записывайте текущее время;
- не используйте случайность без фиксированного seed и явной причины;
- не включайте абсолютные локальные пути;
- удаляйте устаревшие ассеты только в границах точной выходной папки;
- сохраняйте commit исходников игры в метаданных, когда это предусмотрено
  контрактом.

Большой generated diff должен объясняться изменением источника или кода. Если
при повторной сборке без изменений diff появляется снова, это ошибка сборщика.

### 4.8. Валидация и ошибки

Валидатор проверяет не только наличие ключей. В зависимости от контракта нужны:

- точная `schemaVersion`;
- уникальность идентификаторов;
- существование всех ссылок;
- допустимые диапазоны и перечисления;
- согласованность счётчиков и индексов;
- наличие каждого опубликованного ассета;
- отсутствие лишних устаревших ассетов;
- разумный минимальный объём результата, если пустая сборка опаснее ошибки.

Неизвестный обязательный источник или битая ссылка должны останавливать сборку.
Не подменяйте повреждённые данные пустым результатом, который успешно попадёт в
production.

## 5. Репозиторий приложения

### 5.1. Структура

```text
src/App.tsx                 оболочка и верхнеуровневые маршруты
src/modules/registry.tsx    метаданные и подключение модулей
src/modules/<module-id>/    предметный UI, данные и вычисления
src/pages/                  общие страницы
src/admin/                  административная граница
src/styles/                 тема и стили экранов
public/                     статические файлы приложения
public/data/                временный deploy-снимок, не исходный код
docs/                       общая документация проекта
```

Типичный модуль приложения может содержать:

```text
src/modules/<module-id>/
  <ModuleName>Page.tsx      композиция экрана
  config.ts                 URL и локальная конфигурация
  types.ts                  поддерживаемый публичный контракт
  api.ts или store.ts       загрузка, проверка и кэш
  domain.ts / format.ts     чистые расчёты и представление значений
  components/               локальные UI-компоненты
  *.test.ts                 тесты логики и контракта
```

Это ориентир, а не обязательный список. Файл создаётся только при наличии
отдельной ответственности.

### 5.2. Registry и маршруты

`src/modules/registry.tsx` — единственная точка подключения модуля к общей
оболочке. Запись содержит только метаданные маршрута и компонент:

```ts
{
  id: "module-id",
  path: "/module/module-id",
  title: "Полное название",
  summary: "Одно предложение для главной страницы.",
  code: "MOD-00",
  status: "active",
  Component: ModulePage,
}
```

Используйте канонический URL `/module/<module-id>`. Не создавайте отдельный
ручной маршрут для обычного модуля.

`status: "planned"` регистрирует будущий модуль без компонента. При активации
добавляется `Component` и меняется статус; метаданные и путь остаются прежними.

Registry не должен содержать фильтры, расчёты, запросы или JSX внутреннего
экрана. Верхняя навигация также не обязана автоматически показывать каждый
модуль: масштабируемый список находится на главной странице.

### 5.3. Загрузка данных

При deploy каталог `data/` из `ssmc-wiki-data` полностью заменяет `public/data/`
перед сборкой. Поэтому production по умолчанию читает данные с того же origin по
адресу `data/<module-id>/`, без отдельного запроса к GitHub Raw. Полная замена
обязательна: отсутствующий в новом результате файл не должен оставаться в
публикации от предыдущей сборки.

Для локальной разработки независимый источник может получить собственный
корень вида `VITE_<MODULE>_DATA_ROOT`. Это только переопределение адреса;
production-настройки не должны зависеть от него.

Загрузчик обязан:

- собирать URL через `new URL(relativePath, root)`;
- проверять HTTP-ответ;
- проверять `schemaVersion` и минимальную форму документа;
- иметь состояния loading, error и empty;
- не запускать одинаковые параллельные запросы без необходимости;
- корректно работать после повторного открытия экрана;
- не скрывать ошибку сети под пустым каталогом.

Если набор большой, публичная точка входа содержит компактный индекс, а
детальные документы и ассеты загружаются при открытии соответствующей сущности.
Не импортируйте generated JSON в JavaScript bundle.

### 5.4. Типы и предметная логика

TypeScript-типы описывают публичный контракт, а не желаемую форму JSX. На
границе загрузки выполняется runtime-проверка версии и ключевых полей; один
`as Catalog` не является валидацией.

Расчёты, планировщики, классификация представления и сложное форматирование
пишутся как чистые функции без React и DOM. Это позволяет:

- тестировать механику без браузера;
- отделять ошибку данных от ошибки интерфейса;
- переиспользовать вычисление в нескольких компонентах;
- менять оформление без риска изменить результат.

Не дублируйте игровую характеристику константой в приложении, если она может
быть частью контракта. Допустимы только настоящие UI-настройки и явно
документированные временные исключения.

### 5.5. Компоненты и состояние

Корневая страница собирает экран, но не обязана выполнять все вычисления сама.
Разделяйте код, когда появляется самостоятельная ответственность:

- выбор сущности;
- панель результата;
- модальное или боковое описание;
- фильтрация и поиск;
- загрузка данных;
- чистый расчёт.

Состояние хранится как можно ближе к потребителю. URL используется для
состояния, которое должно переживать прямую ссылку или навигацию. `localStorage`
подходит только для безопасных пользовательских настроек и черновиков, но не
для паролей и токенов.

### 5.6. Стили и адаптивность

Глобальная тема и семантические цветовые токены находятся в общем слое стилей.
Модульный CSS отвечает за геометрию конкретного экрана и использует эти токены,
а не создаёт параллельную палитру.

Основные правила:

- layout строится через Grid/Flex, а не абсолютные координаты страницы;
- карточка ограничивает собственный длинный текст и кнопки;
- интерактивные элементы имеют видимый `focus`;
- модальные окна закрываются предсказуемо и не прячут управление за viewport;
- мобильный экран не получает горизонтальный scroll всей страницы;
- локальный горизонтальный scroll допустим для осмысленной одноуровневой ленты;
- учитывается `prefers-reduced-motion`;
- цвет не является единственным способом показать состояние.

Перед PR проверьте хотя бы широкий desktop, обычный ноутбук и телефон. Отдельно
проверьте длинные русские названия, пустой результат, ошибку загрузки и
максимально заполненное состояние.

### 5.7. Административная граница

Административный код живёт отдельно от обычных модулей. Публичная карточка может
использовать уже применённый результат редакторского слоя, но не должна знать
пароль или детали API записи.

Правила безопасности:

- клиентский пароль никогда не считается авторизацией сам по себе;
- секрет не записывается в репозиторий, bundle, URL или `localStorage`;
- право записи проверяет серверная сторона;
- полная перезапись документа защищается проверкой версии/SHA от конфликтов;
- ошибки авторизации не раскрывают секреты;
- полноценная закрытая версия требует серверной сессии и ограничения запросов.

Текущее и запланированное поведение административного слоя различаются. Не
меняйте эту границу без отдельного пункта в roadmap и плана совместимой миграции.

## 6. Изменение контракта между репозиториями

### 6.1. Добавление поля

1. Найдите точный источник в игре.
2. Добавьте нормализацию в соответствующий data-модуль.
3. Добавьте тесты значения по умолчанию и явного переопределения, если оба
   варианта возможны.
4. Расширьте валидатор.
5. Пересоберите данные и изучите generated diff.
6. Опубликуйте совместимое изменение в `ssmc-wiki-data`.
7. Обновите TypeScript-тип, расчёт и отображение в `ssmc-wiki-app`.
8. Добавьте тест приложения на новое поведение.

### 6.2. Ломающее изменение

1. Спроектируйте новую схему и увеличьте `schemaVersion`.
2. По возможности временно публикуйте старое и новое представление вместе.
3. Научите приложение читать новую версию или обе версии переходного периода.
4. Опубликуйте приложение.
5. Только после этого удалите старую форму из данных.

Нельзя сначала удалить поле из production-data, а потом исправлять сайт.

### 6.3. Изменение только интерфейса

Если все необходимые факты уже присутствуют в публичном контракте, data-репо
не меняется. Форматирование, подписи, группировка и визуальная компоновка
являются ответственностью приложения.

## 7. Создание нового модуля

### 7.1. Сначала определите границу

До написания кода ответьте:

- какую пользовательскую задачу решает модуль;
- какие данные ему нужны;
- существует ли уже публичный контракт;
- какие данные компактны, а какие нужно загружать лениво;
- есть ли чистая вычислительная часть;
- какие состояния должны быть доступны по прямой ссылке.

Не объединяйте несвязанные задачи только потому, что они используют один
источник игры.

### 7.2. Data-часть

Если нужен новый набор данных:

1. создайте `scripts/<module_package>/`;
2. реализуйте CLI-сборку без зависимости от локального рабочего каталога;
3. создайте публичную точку входа с `schemaVersion`;
4. разместите результат в `data/<module-id>/`;
5. добавьте валидатор и тесты;
6. добавьте PR-проверку и отдельный publishing workflow;
7. убедитесь в детерминированной повторной сборке.

Публикующий workflow одного модуля не должен случайно пересобирать или
перезаписывать результаты другого. Параллельные workflows, пишущие в одну ветку,
должны использовать общую защиту от конфликтующей публикации.

### 7.3. App-часть

1. создайте `src/modules/<module-id>/`;
2. опишите и проверьте контракт на границе загрузки;
3. вынесите вычисления из React;
4. реализуйте loading, error, empty и рабочее состояние;
5. добавьте модуль в registry;
6. покройте расчёты и преобразования тестами;
7. проверьте прямой URL и возврат на главную;
8. проверьте desktop и мобильный экран.

Если UI ещё не готов, регистрируйте модуль как `planned`, не создавая пустую
реализацию ради статуса `active`.

## 8. Локальная разработка

Клонируйте репозитории рядом:

```text
workspace/
  ssmc-wiki-data/
  ssmc-wiki-app/
  space-stories-cm14/       при работе со сборщиками
```

### 8.1. Data

Требуются Python 3.11+, Git и локальный checkout игры.

```powershell
cd ssmc-wiki-data
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install pytest ruff
python -m pytest scripts
python -m ruff check scripts
```

Параметры конкретного сборщика и валидатора смотрите через CLI:

```powershell
python -m scripts.<module_package>.build --help
python -m scripts.<module_package>.validate --help
```

Перед пересборкой зафиксируйте точный commit игрового checkout:

```powershell
git -C ../space-stories-cm14 rev-parse HEAD
```

### 8.2. App

Требуются Node.js 22 и npm.

```powershell
cd ssmc-wiki-app
npm ci
npm run dev
```

Полная локальная проверка:

```powershell
npm run lint
npm run test
npm run build
```

Для полной локальной проверки создайте одноразовый снимок `public/data/` из
соседнего `ssmc-wiki-data/data/` либо запустите HTTP-сервер и задайте
соответствующий `VITE_<MODULE>_DATA_ROOT`. Корень URL должен заканчиваться `/`.
Снимок не коммитится и не правится вручную: источником истины остаётся data-репозиторий.

Не открывайте `index.html` напрямую с диска: Vite нужен для ES-модулей,
маршрутизации и dev proxy.

## 9. Тесты

Тестируйте поведение на самой низкой полезной границе.

Для сборщика:

- разрешение наследования и значений по умолчанию;
- нормализация игровых компонентов;
- связи и граничные случаи графа;
- конфигурация и ошибочные входы;
- публичная схема и валидатор;
- регрессия конкретной найденной ошибки.

Для приложения:

- чистые вычисления;
- преобразование контракта в представление;
- поиск, фильтрация и сортировка как функции;
- поддерживаемые и неподдерживаемые версии схемы;
- значения по умолчанию и отсутствие необязательных полей;
- регрессия найденной ошибки.

Тест не должен зависеть от сети или текущего содержимого production, если это не
отдельный интеграционный тест. Используйте маленькие fixtures, показывающие смысл
проверки.

## 10. Git и pull request

### 10.1. Объём изменения

Один PR решает одну связанную задачу. Не смешивайте изменение контракта,
несвязанный redesign и массовое форматирование.

Соблюдайте границы чужих изменений в рабочем дереве. Не удаляйте неизвестные
файлы и не перегенерируйте все наборы, если задача касается одного модуля.

### 10.2. Что описать в PR

- проблема и пользовательский результат;
- источник игровой механики, если меняются данные;
- изменение публичного контракта и его совместимость;
- причина generated diff;
- выполненные проверки;
- ручная UI-проверка, если менялся интерфейс;
- миграция или порядок публикации, если затронуты оба репозитория.

### 10.3. Проверки перед PR

Data:

```powershell
python -m ruff check scripts
python -m pytest scripts
python -m scripts.<module_package>.validate --help  # затем запустите с реальными путями
```

App:

```powershell
npm run lint
npm run test
npm run build
```

Также выполните `git diff --check` и изучите `git diff --stat`. Не коммитьте
`node_modules/`, `dist/`, `.venv/`, кэши Python, локальные секреты и временные
рендеры.

## 11. Типичные ошибки

- Ручная правка `data/<module>/catalog.json` вместо изменения сборщика.
- Чтение сайтом диагностического `index.json`.
- Парсинг игрового YAML непосредственно в браузере.
- Новое обязательное поле без увеличения версии несовместимой схемы.
- Публикация приложения раньше требуемых данных.
- Бизнес-логика в registry, `App.tsx` или JSX-компоненте.
- Копирование предметной логики между модулями.
- Общая абстракция без второго потребителя.
- Загрузка всех больших ассетов при входе в модуль.
- Проглатывание ошибки сети и показ пустого результата.
- Цветовые литералы в компоненте вместо семантических токенов темы.
- Хранение административного пароля в клиентском постоянном хранилище.

## 12. Definition of Done

Изменение готово к слиянию, когда:

- ответственность находится в правильном репозитории и модуле;
- контракт структурирован, версионирован и провалидирован;
- generated data получены воспроизводимой сборкой;
- вычисления отделены от интерфейса;
- добавлены тесты на новое поведение и найденные граничные случаи;
- все проверки затронутых репозиториев проходят;
- обработаны loading, error, empty и максимально заполненное состояние;
- интерфейс проверен на широком, обычном и мобильном экране;
- документация меняется только тогда, когда изменилось устойчивое правило,
  команда запуска или публичная граница;
- в PR понятен безопасный порядок публикации.

Запланированные, но ещё не действующие решения находятся только в
[`ROADMAP.md`](ROADMAP.md). До их завершения источником истины остаются текущий
код, публичные схемы и это руководство.
