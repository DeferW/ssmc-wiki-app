# Руководство контрибьютора SSMC Wiki

Это руководство описывает архитектуру и совместную разработку двух
репозиториев:

- `DeferW/ssmc-wiki-data` — воспроизводимые сборщики данных из прототипов игры;
- `DeferW/ssmc-wiki-app` — модульное React-приложение, читающее публичные JSON.

Главное правило: **сборщик объясняет механику игры, приложение решает, как её
показать**.

## 1. Общий поток данных

```text
репозиторий игры + config
            │
            ▼
ssmc-wiki-data / scripts/<module>
            │  resolve → relations → normalize → validate
            ▼
data/<module>/catalog.json + ассеты
            │
            ▼
ssmc-wiki-app / src/modules/<module>
            │  load → format → render
            ▼
пользовательский интерфейс
```

Приложение не должно разбирать YAML игры, разрешать наследование прототипов или
читать диагностический `index.json`. Если сайту не хватает поля, оно сначала
добавляется в публичный контракт сборщика.

## 2. Границы модулей

Предметные модули изолированы и не импортируют друг друга.

```text
ssmc-wiki-data/scripts/       ssmc-wiki-app/src/modules/
  common/                       registry.tsx
  catalog/                      equipment/
  chemistry/                    chemistry/
  mobs/                         mobs/
```

Новый модуль создаётся как `scripts/<module-id>/` и
`src/modules/<module-id>/`. Общий код
выносится только после появления второго реального потребителя.

## 3. Репозиторий данных

### Назначение

`ssmc-wiki-data` преобразует изменчивые игровые прототипы в стабильные,
небольшие контракты. Он отвечает за:

- чтение YAML и Fluent-локализации;
- разрешение родителей и компонентов;
- обход содержимого и технических зависимостей;
- нормализацию механических характеристик;
- автоматическую классификацию;
- применение редакторских overrides;
- подготовку спрайтов;
- валидацию и публикацию generated data.

### Структура

```text
config/
  catalog-sources.yml
  catalog-overrides.json
scripts/
  common/
  catalog/
  chemistry/
  mobs/
data/
  catalog/
  chemistry/
  mobs/
.github/workflows/
requirements.txt
pyproject.toml
```

`scripts/common/prototypes.py` содержит общий resolver прототипов, а
`scripts/common/localization.py` — общую Fluent-локализацию. Предметная логика
остаётся в своём модуле.

## 4. Конвейер каталога

Корни обхода задаёт `config/catalog-sources.yml` schema v3:

- `vendors` — точные prototype ID торговых автоматов;
- `cargoCatalogs` — консоли заказов карго;
- `classification` — узкие правила исключений и канонизации.

Сборка выполняет следующие этапы:

1. Загружает и разрешает игровые прототипы.
2. Читает товары указанных автоматов и заказы карго.
3. Обходит граф от торговой записи до вложенных и конечных предметов.
4. Строит связи: содержимое, магазин, патрон, projectile, установленный обвес,
   совместимость и ключи гарнитур.
5. Автоматически назначает одну категорию.
6. Нормализует только полезные конкретному предмету блоки характеристик.
7. Применяет `catalog-overrides.json` после автоклассификации.
8. Рендерит спрайты, формирует JSON и запускает валидацию.

### Файлы `scripts/catalog`

- `build.py` — CLI-точка входа и полный конвейер.
- `catalog.py` — оркестратор источников, графа и карточек.
- `classification.py` — правила автоматических категорий.
- `config.py` — проверка sources/overrides и применение редакторских категорий.
- `core.py` — категории, слоты, отношения и разрешённые публичные компоненты.
- `prototypes.py` — каталожные парсеры размеров, сеток и реагентов.
- `relations.py` — ориентированные связи предметов и совместимость.
- `statistics.py` — нормализованные блоки механики.
- `sprites.py` — извлечение PNG из RSI/PNG игры.
- `reporting.py` — запись результатов, review и сравнение сборок.
- `validate.py` — проверка схемы и согласованности всех результатов.
- `test_*.py` — модульные и интеграционные тесты каталога.

### Блоки характеристик

Каталог публикует блок только там, где он семантически полезен:

- `weaponStats` — режимы и параметры стрельбы;
- `armorStats` — защита и модификаторы движения;
- `attachmentStats` — эффекты и условия обвесов;
- `storageStats` — вместимость и осмысленные ограничения содержимого;
- `solutionStats` — полезное химическое содержимое;
- `communicationStats` — каналы, ключи, передача и приём;
- `skillStats` — навыки и уровни обучающих предметов.

Сборщик сохраняет механику, а не готовую фразу UI. Например, `walkModifier`
остаётся числом, а приложение показывает округлённое замедление в процентах.

## 5. Категории и overrides

Итоговые категории:

`Оружие`, `Боезапас`, `Обвесы`, `Броня`, `Экипировка`, `Медицина`,
`Снаряжение`, `Другое`, `Скрытые`.

`Скрытые` — категория, а не `hidden: true`. Классификатор никогда не назначает
её автоматически.

Канонический документ overrides:

```json
{
  "schemaVersion": 2,
  "items": {
    "PrototypeId": {
      "category": "Скрытые"
    }
  }
}
```

Пустой файл, `{}` и `{ "schemaVersion": 2, "items": {} }` означают отсутствие
редакторских изменений. Override применяют для единичного редакторского решения.
Систематическую ошибку семейства предметов исправляют в классификаторе и тестах.

## 6. Публичный и диагностический JSON

`data/catalog/catalog.json` — публичный контракт сайта. Он содержит карточки,
источники покупки и цены, нормализованные характеристики, связи, категории,
aliases, спрайты и метаданные overrides.

`data/catalog/index.json` — диагностический граф сборщика: полные торговые записи,
происхождение и внутренние отношения. Его схема может меняться без поддержки
приложением.

Если UI нужно новое поле:

1. Найдите источник поля в игровых прототипах.
2. Нормализуйте его в `statistics.py` или подходящем модуле.
3. Добавьте тест и проверку `validate.py`.
4. Пересоберите `catalog.json`.
5. Обновите TypeScript-тип и отображение сайта.

Не подключайте `index.json` как короткий путь к сырому полю.

## 7. Локальная работа со сборщиком

Требуются Python 3.11+, Git и локальная копия игры.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install pytest ruff
```

Сборка каталога:

```powershell
python -m scripts.catalog.build `
  --game-source ../space-stories-cm14 `
  --config config/catalog-sources.yml `
  --index-output data/catalog/index.json `
  --output data/catalog/catalog.json `
  --sprites-output data/catalog/sprites `
  --commit GAME_COMMIT `
  --locale ru-RU
```

Проверки:

```powershell
python -m pytest scripts
python -m ruff check scripts
python -m scripts.catalog.validate `
  --catalog data/catalog/catalog.json `
  --index data/catalog/index.json `
  --config config/catalog-sources.yml `
  --sprites data/catalog/sprites
```

Generated data изменяется сборкой, а не ручным редактированием.

## 8. Другие сборщики и workflows

`scripts/chemistry` формирует данные химии, `scripts/mobs` — данные существ.
У каждого модуля собственные build, validator, тесты, `data/<module-id>/` и
publishing workflow.

Публикующие workflows используют общую concurrency-группу, чтобы два job не
записывали разные generated data в `main` одновременно. `pr-checks.yml`
проверяет код до публикации.

## 9. Репозиторий приложения

Технологии: React 19, TypeScript, Vite, React Router `HashRouter`, Vitest и
ESLint. Hash-маршруты подходят GitHub Pages и не требуют серверного fallback.

```text
src/
  main.tsx
  App.tsx
  admin/
  modules/
  pages/
  styles/
public/
docs/
```

- `main.tsx` монтирует приложение и подключает CSS.
- `App.tsx` создаёт оболочку и маршруты из registry.
- `pages/HomePage.tsx` показывает все зарегистрированные модули.
- `pages/PlaceholderPage.tsx` обслуживает запланированные модули.
- `pages/NotFoundPage.tsx` обрабатывает неизвестные URL.
- `styles/base.css` хранит единственные глобальные цветовые токены.
- `styles/home.css`, `equipment.css`, `chemistry.css`, `responsive.css` содержат
  правила экранов.

## 10. Registry веб-модулей

`src/modules/registry.tsx` — единственная точка подключения модуля к оболочке.

```ts
type ModuleDefinition = {
  id: string;
  path: string;
  title: string;
  shortTitle: string;
  summary: string;
  code: string;
  status: "active" | "planned";
  Component?: ComponentType;
};
```

`status: "planned"` создаёт точный маршрут `module.path` с placeholder.
`status: "active"` и `Component` подключают готовую страницу. URL имеет вид
`/<module-id>`; маршрут `/module/:moduleId` не используется.

Пример активации:

```ts
import { ChemistryPage } from "./chemistry/ChemistryPage";

{
  id: "chemistry",
  path: "/chemistry",
  title: "Химический планировщик",
  shortTitle: "Химия",
  summary: "Реагенты, реакции и маршруты приготовления.",
  code: "CHM-06",
  status: "active",
  Component: ChemistryPage,
}
```

## 11. Модуль equipment

```text
src/modules/equipment/
  EquipmentPage.tsx
  catalogStore.ts
  config.ts
  format.ts
  format.test.ts
  types.ts
  usePanelSettings.ts
  components/
```

- `EquipmentPage.tsx` — поиск, фильтры, сортировка, выбранный предмет и admin UI.
- `catalogStore.ts` — единая загрузка и кэш публичного JSON.
- `types.ts` — TypeScript-контракт карточек.
- `config.ts` — URL данных и порядок категорий.
- `format.ts` — чистые преобразования технических значений.
- `usePanelSettings.ts` — локальная настройка положения карточки.
- `FilterPanel.tsx` — открытие категории и независимый checkbox-мультифильтр.
- `DetailsPanel.tsx` — описание, связи и блоки подробностей.
- `StatBlocks.tsx` — покупка, оружие, projectile, броня, обвесы, медицина,
  хранение, связь, обучение и ношение.
- `CatalogSettings.tsx` — локальная кнопка CFG.
- `ItemSprite.tsx`, `ItemLinks.tsx` — спрайты и связанные предметы.

Скрытый предмет исключается только из обычной сетки. Он остаётся в
`catalog.items`, поэтому открывается через связь или URL-параметр `item`.

## 12. Модуль chemistry

```text
src/modules/chemistry/
  ChemistryPage.tsx
  config.ts
  effects.ts
  effects.test.ts
  planner.ts
  planner.test.ts
  types.ts
```

- `ChemistryPage.tsx` загружает контракт, показывает каталог и форму плана.
- `types.ts` описывает публичный JSON и результат расчёта.
- `config.ts` задаёт независимый корень `VITE_CHEMISTRY_DATA_ROOT`.
- `effects.ts` переводит игровые эффекты, условия и пороги в понятные игроку
  описания; React-компонент не интерпретирует YAML-теги самостоятельно.
- `planner.ts` содержит чистый алгоритм без React и DOM: строит граф реакций,
  выбирает рецепт, разворачивает промежуточные реагенты, группирует одинаковые
  приготовления и раскладывает объёмы по ёмкостям.
- `planner.test.ts` проверяет партии, вместимость, дробные пропорции и режимы
  переливания.

Планировщик считает воду и элементы из `catalogSections.elements` исходными
реагентами химмастера. Остальные реагенты рекурсивно раскрываются до этих
источников. Промежуточные вещества всегда готовятся в мензурках по 100u. Финал
готовится либо в таких же мензурках, либо в одном баке до 1000u; в бак реагенты
переносятся порциями не более 100u.

Доступные кнопки химмастера: `1`, `5`, `10`, `15`, `20`, `25`, `30`, `50`,
`100` и `ALL`. Алгоритм подбирает точную последовательность; `ALL` применяется
только когда выбранный объём ровно заполняет оставшееся место мензурки. Если
запрошенный объём не помещается в бак, план возвращает понятную ошибку, а режим
мензурок автоматически создаёт нужное число партий.

Все игровые данные берутся из `data/chemistry/catalog.json`; UI не содержит
вручную переписанного списка рецептов. Поэтому изменение схемы сначала делается
в `ssmc-wiki-data`, затем отражается в `types.ts` и отображении.

## 13. Admin-редактор каталога

Тестовый маршрут: `#/equipment/admin`. Его UI доступен всем, но запись защищена
паролем Cloudflare Worker.

```text
src/admin/equipment/
  AdminEquipmentPage.tsx
  api.ts
  types.ts
  useAdminOverrides.ts
```

- сохранённые overrides и SHA загружаются через Worker;
- при временной ошибке чтения используется публичный GitHub Contents fallback;
- правки до пароля хранятся как локальный черновик;
- пароль существует только в состоянии вкладки;
- выбор автоматической категории удаляет запись из overrides;
- сохранение полностью перезаписывает schema v2 и использует SHA от конфликтов;
- индивидуальные и групповые правки используют один draft;
- все предметы, присутствующие в overrides, отмечаются `EDITED`.

Worker должен считать отсутствующий или нулевой файл пустым документом schema v2.
Production CORS должен разрешать origin сайта. Полноценная закрытая версия в
будущем потребует серверной сессии, rate limit, CSRF-защиты и журнала изменений.

## 14. Цветовая система и UX

Все глобальные цвета объявляются только в `styles/base.css`:

- `--accent`, `--accent-soft` — действия, выбор и успешные состояния;
- `--warning`, `--warning-line` — только `EDITED` и «В разработке»;
- `--danger`, `--danger-line` — настоящая ошибка;
- `--text*`, `--muted*` — иерархия текста;
- `--line*`, `--surface*`, `--bg` — рамки и поверхности.

Не добавляйте новый цветовой литерал в компонент без нового семантического
состояния. Не используйте красный или жёлтый как украшение.

Перед PR проверьте 1920×900, 1280×720 и телефон 390×844, отсутствие
горизонтального scroll, клавиатурный focus, Escape в диалоге, состояния loading,
error и пустого поиска, а также `prefers-reduced-motion`.

## 15. Локальная работа с сайтом

Требуются Node.js 22 и npm.

```powershell
npm ci
npm run dev
npm run lint
npm run test
npm run build
```

Для совместной проверки двух репозиториев:

```powershell
cd ../ssmc-wiki-data/data/catalog
python -m http.server 4174
```

В другом терминале:

```powershell
$env:VITE_CATALOG_DATA_ROOT="http://127.0.0.1:4173/catalog-data/"
npm run dev -- --host 127.0.0.1 --port 4173
```

Vite проксирует `/catalog-data` на порт 4174 и `/admin-api` на Worker.
`dist/`, `node_modules/`, `.venv` и временные результаты не коммитятся.

## 16. Создание нового веб-модуля

1. Выберите устойчивый `module-id` в kebab-case.
2. Создайте `src/modules/<module-id>/`.
3. Добавьте корневую `<ModuleName>Page.tsx`.
4. Добавьте локальные types, config, store, formatters и components по мере нужды.
5. Покройте вычисления и преобразования тестами.
6. Зарегистрируйте `planned`-карточку с коротким URL.
7. После готовности добавьте `Component` и смените status на `active`.
8. Проверьте прямой URL, главную, desktop и телефон.

Новый контракт данных должен иметь собственные `data/<module-id>`,
`schemaVersion`, validator, тесты сборщика, workflow, загрузчик и TypeScript-типы.

## 17. Порядок изменения контракта

Добавочное изменение — новое необязательное поле. Ломающее изменение — удаление,
переименование или изменение смысла; оно требует новой `schemaVersion` и
синхронного обновления приложения.

Если сайту требуется новое поле:

1. Реализуйте и опубликуйте изменение в `ssmc-wiki-data`.
2. Дождитесь успешной сборки generated data.
3. Затем обновите `ssmc-wiki-app`.

Так production не ожидает контракт, которого ещё нет.

## 18. Чек-лист PR

### Сборщик

- Источник найден в прототипах игры, а не угадан.
- Поле нормализовано и полезно игроку.
- Есть тест и валидация.
- `pytest`, Ruff и validator проходят.
- Generated diff объясним.
- Чужие модули не связаны новым импортом.

### Сайт

- Код находится в `src/modules/<module-id>` или оправданной admin-границе.
- Registry содержит точный короткий URL.
- Используется публичный `catalog.json`, не `index.json`.
- Техническое форматирование вынесено из JSX.
- Ошибки загрузки обработаны.
- Новые цвета используют семантические токены.
- ESLint, тесты, TypeScript и production build проходят.
- Проверены desktop, ultrawide и телефон.
- Секреты не попали в bundle или `localStorage`.

## 19. Неизменяемые архитектурные решения

- Публичный сайт читает контракт, а не внутренности сборщика.
- `index.json` остаётся диагностическим.
- Один предмет имеет одну итоговую категорию.
- `Скрытые` назначается только override.
- Предметные модули изолированы по папкам.
- Общая абстракция появляется после второго применения.
- Registry регистрирует модуль, но не содержит бизнес-логику.
- URL модуля имеет вид `/<module-id>`.
- Admin-пароль проверяется Worker, а не React-кодом.
- Generated data меняется сборкой.

Запланированная миграция редакторских overrides из сборщика в приложение
зафиксирована в [`ROADMAP.md`](ROADMAP.md). Пока она не реализована, описанный
выше текущий контракт остаётся действующим.

## 20. Быстрый старт контрибьютора

1. Клонируйте оба репозитория рядом.
2. Запустите все тесты без изменений.
3. Для data-задачи найдите исходный компонент игры и нормализатор.
4. Для UI-задачи найдите публичный JSON и соответствующий веб-модуль.
5. Сделайте минимальное изолированное изменение.
6. Добавьте или обновите тест.
7. Запустите проверки затронутого репозитория.
8. Проверьте UI на трёх размерах экрана.
9. В PR объясните изменение контракта, generated data и поведения UI.

Эти границы позволяют добавлять новые модули без превращения сборщика и сайта
в общий монолит.
